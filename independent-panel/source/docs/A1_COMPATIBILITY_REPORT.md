# گزارش سازگاری با A1 — اختلاف‌ها و خطرهای انتقال

دامنهٔ بررسی: سه فایل مرجع + سورس کامل ZIP + کد فعلی این پروژه.
این گزارش **تصمیم اجرایی نیست**؛ فهرست خطر و پیشنهاد است. هیچ تغییری در A1 انجام نشده است.

## ۱. وضعیت مدل داده

| مورد | عدد |
| --- | --- |
| جدول‌های A1 | 62 |
| موجودیت‌های ساخته‌شده برای جدول‌های A1 | 61 (+ `users` ↔ User داخلی) |
| موجودیت‌های اختراعی حذف‌شده | 5 (`Agent`, `Currency`, `Remittance`, `CashAccount`, `Transaction`) |

## ۲. خطرهای بحرانی

### خ-۱. نبود احراز هویت و جداسازی صرافی

- A1: RLS روی هر ۶۲ جدول فعال + `exchange_code` + هدر `x-app-token`.
- این نسخه: دسترسی باز، نقش شبیه‌سازی‌شده.
- خطر: هر بازدیدکننده می‌تواند همهٔ داده‌ها را بخواند/تغییر دهد. برای پیش‌نمایش قابل قبول، برای
  استفادهٔ واقعی غیرقابل قبول.
- پیشنهاد (اجرا نشده): فعال‌سازی ورود، افزودن `exchange_id` به User، و RLS بر پایهٔ آن.

### خ-۲. نبود ثبت اتمیک و ضد تکرار

- A1: RPC `post_document_transaction` + `idempotency_keys` یکتا.
- این نسخه: چند فراخوانی SDK؛ در صورت خطا سند نیمه‌کاره پاک می‌شود.
- خطر: سند بدون ردیف، یا سند تکراری با دو بار کلیک.
- پیشنهاد: backend function واحد برای ثبت سند + کلید عملیات اجباری.

### خ-۳. ادغام جدول‌های عملیاتی در مسیر ثبت

- `bank_transactions`, `treasury_transactions`, `conversions`, `journal_entries` در A1 جدول مستقل‌اند.
- در این نسخه مسیر ثبت فقط `Document` می‌نویسد.
- خطر: گزارش مستقیم از این جدول‌ها در A1 در نسخهٔ مرجع خالی می‌ماند و مقایسهٔ دو نسخه گمراه‌کننده می‌شود.
- پیشنهاد: نوشتن موازی یا انتخاب رسمی یکی از دو مسیر (تعارض باز شمارهٔ ۱ تا ۴ در DECISIONS).

## ۴. نامعلوم‌های فایل مرجع (باید از منبع زنده تأیید شود)

1. ایندکس‌ها: در فایل مرجع وجود ندارند.
2. متن policyهای RLS: فقط `rls_enabled` ثبت شده.
3. مقادیر کامل CHECK: `customers.identity_status`, `chart_of_accounts.account_type`,
   `fiscal_periods.status`, `languages.direction`, `demo_preview_records.record_kind`,
   `layout_hex_references.mime_type` در فایل بریده شده‌اند.
4. ستون مبدأ ۲۶ رابطهٔ خارجی `undefined` است (۱۶ مورد در `users` و `exchanges`).
5. وضعیت runtime قابلیت‌ها: `feature_settings` بدون داده است؛ وضعیت‌های `updating` فقط از
   `FEATURE_CATALOG` کد استخراج شده و ممکن است در دیتابیس زنده متفاوت باشد.
6. جدول `chat_groups` دو رابطهٔ `group_id` تکراری دارد که با ستون‌هایش نمی‌خواند.

پنل فروشنده، رسید/چاپ، دفتر حواله، مغایرت‌گیری، سند دستی.

## ۷. پیشنهادهای امنیتی (اجرا نشده)

1. RLS فقط بر اساس `exchange_id` کاربر؛ `created_by_id` برای رکوردهای شخصی.
2. نقش `creator` فقط با `builder_access` قابل اعطا باشد.
3. `app_auth_secret` هرگز در موجودیت عمومی خوانده نشود؛ در Secret بستر نگهداری شود.
4. عملیات مالی فقط از backend function با اعتبارسنجی ورودی.
5. مسدودسازی حذف مالی بدون ثبت `reason` و رد حسابرسی.
